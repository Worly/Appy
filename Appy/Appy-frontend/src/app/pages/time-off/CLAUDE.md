# CLAUDE.md — Time Off Page (pages/time-off/)

Manages a facility's time-off (blocked availability). Requires `LoggedInGuard` + `SelectedFacilityGuard`. Lazy-loaded.

## Routes
- `/time-off` → `TimeOffComponent` — tabbed list (One-offs / Recurring / Holidays). Active tab + scope persist in the URL (`?tab=oneoff|recurring|holidays&scope=upcoming|history`).
- `/time-off/new?type=oneoff|recurring`, `/time-off/edit/:id` → `TimeOffEditComponent`.
- `/time-off/holiday/edit/:id` → `TimeOffEditComponent` with `data: { holiday: true }` — holiday mode.

## Model
A `TimeOff` rule has a `recurrence` (OneOff / Weekly / Monthly), a required `label`, optional `notes`, an all-day flag or a time range, and recurrence-specific fields (date range for one-off; day-of-week or day-of-month + optional effective bounds for recurring). `TimeOffListType` (`OneOff` | `Recurring`) and `TimeOffScope` (`Active` | `History`) are API-facing tokens for the list endpoint. `TimeOff.importedHolidayId` links a generated time-off back to its source `Holiday` (set by the import job; read-only on the frontend). See `models/time-off.ts`.

## Container & list
`TimeOffComponent` hosts three tabs (each with an icon: One-off `calendar-day`, Recurring `arrows-rotate`, Holidays `umbrella-beach`) and a `Upcoming | History` scope switch (icons `arrow-right` / `clock-rotate-left`), shown on every tab — both are `app-segmented-control` (the shared single-select pill toggle; the editor's Weekly/Monthly and apply-from toggles use it too). The scope switch shares a `.controls` row with the tab's primary action — an **icon-only** dashed-outlined button (icon-only so the row never wraps on narrow screens; `title`/`aria-label` keep it discoverable): a `+` add button on the One-off/Recurring tabs, and a gear "configure auto-import" button on Holidays. It renders `app-time-off-list` for the active (type, scope) and opens `app-single-time-off` in an `app-dialog` on row click. `SingleTimeOffComponent` is **exported** from `TimeOffModule` so the appointments list can open the same details dialog when a time-off is clicked there. It accepts an `@Input() holiday?: Holiday` for direct holiday binding (container path) or loads via the existing `@Input() id` — when the loaded `TimeOff` has `importedHolidayId != null`, it fetches the `Holiday` via `HolidayService.getById` and shows holiday treatment (appointments-view bridge). Holiday mode renders provenance, changes block (when `isEdited`), and Revert/Remove actions with confirm dialogs. `@Output() onChanged` fires after revert or remove so the container can refetch. `AllDayTimeOffPickerComponent` (`app-all-day-time-off-picker`) is a small presentational pick-list (umbrella header + day subtitle + one tappable row per occurrence, emitting `pick`) — also **exported** and used by both appointments views to choose among a day's several all-day time-offs; the host owns the dialog and opens the details view on `pick`. The **Holidays tab** renders a forward-paginated list of `Holiday` items via `HolidayService.getList(scope)` with infinite-scroll (same pattern as `TimeOffListComponent`). When empty, it shows an empty state with a CTA that opens the configure dialog (`configureAutoImport()`). Row click opens the details dialog (`app-single-time-off [holiday]`) for active/edited holidays, or the restore dialog for removed ones. The configure dialog (`#configureDialog`) lets the user pick a country code and save settings via `HolidayService.saveSettings`; if the country changes while imported holidays exist, a confirm-change dialog gates the save first. `+ New` routes to the editor with `?type=` matching the tab.

`app-time-off-list` is a forward-only paginated list (via `TimeOffService.getList` → `pagedQuery`). **Active** is bounded (typically one page); **History** grows unbounded and paginates on scroll, ordered most-recently-ended first. Rows render via `app-single-time-off-list-item`. Schedule/time strings come from the pure helpers in `time-off-display.ts`: `timeOffScheduleText` (one-off date range, or "Every Monday" / "Every 9th of month" — the monthly day rendered as a locale-aware ordinal, so it takes the active language code), `timeOffRecurringRangeText` (a recurring rule's effective span — "from – until" when bounded, "From <date>" when open-ended; empty for one-offs), `timeOffDayCountText` (inclusive one-off day count, humanized & pluralized per locale — "1 day"/"4 days", "1 dan"/"4 dana"; empty for recurring or an invalid/incomplete range), and `timeOffTimeText`. Both the list row and the `app-single-time-off` details dialog show the recurring effective span alongside the recurrence.

## Editor
`TimeOffEditComponent` is a single component with no recurrence dropdown. Type is fixed on entry (`?type=` on new; from the loaded rule on edit) and cannot be changed (no One-off↔Recurring conversion). When entered via `holiday/edit/:id` (`data: { holiday: true }`), the component operates in **holiday mode** (`isHolidayMode = true`): it loads the holiday via `HolidayService.getById`, projects it onto a one-off `TimeOff` form with the label locked (hidden input, shown as page title), hides recurrence controls and the To-date row (single-day only — `onStartDateChange` keeps `endDate` in lockstep), saves via `HolidayService.edit`, and removes via `HolidayService.remove`. The split/apply-from dialog never fires in holiday mode. Recurring uses a `Weekly | Monthly` segmented control. New time-offs default to all-day (the 9–17 time range is still pre-filled for when the user turns all-day off). Delete lives here. Saving a recurring edit opens the "apply changes" dialog **only when the start date was not changed** — moving the From date is direct timeline editing, so it saves in place with no fork (gated in `save()` against `originalStartDate`, captured on load). When shown, the dialog offers "From a date" (default today, forks the rule's timeline via `TimeOffService.saveWithSplit` → `PUT edit?applyFrom=`, splitting it into two entries) or "All occurrences" (a plain in-place edit). It shows an info hint explaining the effect of the selected mode (`APPLY_FROM_SPECIFIC_HINT` / `APPLY_FROM_ALL_HINT`). An end-date-only change still opens the dialog. Every date selector in the editor (and the dialog) uses `showDayOfWeek` so the weekday is shown with the date; the day-of-week / day-of-month / time dropdowns use `matchTriggerWidth` so their option panels line up with the full-width inputs. One-off edits save directly. On a one-off, moving the From date drags the To date with it while the two are equal (a single-day range), so single-day time-offs stay single-day; a multi-day range leaves its To untouched. The one-off editor also shows the inclusive day count (`timeOffDayCountText`) right-aligned beside the "To" label, live-updating as the dates change; the `app-single-time-off` details dialog shows the same count as an info row (one-offs only). Recurring rules always carry an effective-from (the always-shown "From", defaulting to today); a separate "Set an end date" toggle controls only the optional "until" bound and never clears the start. (Effective-from is mandatory for every recurrence — the backend rejects a missing start rather than defaulting it.) Delete always opens a confirmation dialog. For an active, already-started recurring rule (`canStopRecurring` in `time-off-display.ts` gates it) the dialog offers **End it** — stop the rule at yesterday via `TimeOffService.stop` → `PUT stop/{id}`, keeping past occurrences — vs **Delete entirely** (the hard delete). One-off, ended, future, and today-starting rules show a plain "are you sure" confirmation that hard-deletes on confirm.

## Service
`TimeOffService` extends `BaseModelService` (CRUD) and adds `getList(type, scope)` → `PagedResult<TimeOff>` (calls `GET /timeOff/getList`). Mutations invalidate `timeOffKeys.all` (prefix-matching the list keys) and `appointmentKeys.all`, so both the time-off lists and the appointment list refetch automatically. Also adds `saveWithSplit(timeOff, applyFrom?)` which appends the applyFrom query param for recurring timeline forks. Also adds `stop(id)` → `PUT stop/{id}` (clamp a recurring rule's end to yesterday), invalidating the same keys as delete.

## Ordering (backend)
The list endpoint orders per quadrant: One-off/Active by start date (ongoing first); One-off/History & Recurring/History by end date descending; Recurring/Active by each rule's next occurrence on/after today (rules with no remaining occurrence sort last). Filtering and scope classification (`endDate == null || endDate >= today` = Active) run on the DB; only Recurring/Active is ordered in memory (next-occurrence math has no SQL form) — see `TimeOffService.GetList` / `OrderRecurringByNextOccurrence` / `NextOccurrenceOnOrAfter`.

## Display elsewhere
Expansion is backend-owned. The scroller renders occurrences as a hatched band (bundled in the `CalendarDay` response), clickable to open the `app-single-time-off` details dialog. The appointment list view receives occurrences bundled with its page response. Booking blocks slots that overlap a time-off interval (`AppointmentService`).
